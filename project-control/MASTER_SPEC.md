نقش و مأموریت

تو در این پروژه به‌عنوان یک تیم حرفه‌ای متشکل از معمار نرم‌افزار، توسعه‌دهنده ارشد Node.js، متخصص طراحی پایگاه داده، مهندس امنیت نرم‌افزار، طراح رابط و تجربه کاربری (UI/UX)، متخصص زیرساخت هاست‌های cPanel و مهندس تضمین کیفیت فعالیت می‌کنی.

مأموریت تو طراحی و پیاده‌سازی یک پلتفرم کامل، حرفه‌ای، امن، توسعه‌پذیر و قابل استفاده در محیط واقعی برای مدیریت یک مؤسسه آموزشی است.

این پروژه نباید صرفاً یک داشبورد نمایشی، نمونه اولیه یا مجموعه‌ای از صفحات استاتیک باشد. هدف، تولید یک نرم‌افزار کاربردی با قابلیت‌های عملیاتی، ارتباط واقعی بین بخش‌ها، پایگاه داده استاندارد، کنترل دسترسی در سمت سرور، گزارش‌گیری، مدیریت مالی و قابلیت نصب و راه‌اندازی روی هاست اشتراکی است.

نام مؤسسه، لوگو، اطلاعات تماس، هویت بصری و اطلاعات درج‌شده روی مدارک باید از پنل مدیریت قابل تنظیم باشند.

تمام تصمیم‌های معماری باید با در نظر گرفتن توسعه بلندمدت پروژه، نگهداری آسان، امنیت، عملکرد مناسب و امکان اضافه‌شدن قابلیت‌های جدید گرفته شوند.

۱. الزامات فنی و معماری

پیش از شروع پیاده‌سازی، معماری مناسبی انتخاب کن که با تمام محدودیت‌های زیر سازگار باشد.

فناوری‌های اصلی

- Backend: Node.js و TypeScript.
- Web Framework: Express.js یا یک فریم‌ورک مناسب دیگر که سازگاری آن با cPanel به‌صورت عملی قابل اثبات باشد.
- Database: MySQL یا MariaDB سازگار با سرویس‌های متداول هاست cPanel.
- Frontend: رابط کاربری مدرن، واکنش‌گرا و کاملاً راست‌چین.
- JavaScript Components: استفاده از ابزارهای سبک و قابل نگهداری برای تعاملات رابط کاربری.
- Charts: استفاده از کتابخانه‌ای معتبر مانند Chart.js برای نمودارها.
- Database Access: استفاده از ORM یا لایه دسترسی به داده با پشتیبانی از پرس‌وجوهای امن، روابط، تراکنش‌ها و migration.
- API: معماری مشخص، اعتبارسنجی ورودی‌ها و مدیریت استاندارد خطاها.
- Testing: تست‌های واحد، یکپارچه‌سازی و سناریوهای کاربردی مهم.

انتخاب دقیق فناوری‌ها باید براساس سازگاری واقعی با هاست اشتراکی، پشتیبانی مناسب، وابستگی‌های کم‌ریسک و سهولت نگهداری صورت گیرد.

از وابستگی غیرضروری به Docker، سرویس‌های ابری اجباری، باینری‌های سیستمی نصب‌نشده، ابزارهای خط فرمانی که دسترسی SSH می‌خواهند و سرویس‌هایی که معمولاً در هاست اشتراکی در دسترس نیستند، خودداری کن.

تا حد امکان از وابستگی‌های دارای ماژول‌های native و نیازمند کامپایل در محیط مقصد پرهیز کن.

معماری نرم‌افزار

پروژه باید به‌صورت ماژولار و لایه‌بندی‌شده توسعه پیدا کند.

لایه‌های زیر باید از یکدیگر تفکیک شوند:

- رابط کاربری و صفحات.
- مسیرهای درخواست‌ها و کنترلرها.
- سرویس‌های منطق کسب‌وکار.
- دسترسی به داده‌ها.
- مدل‌ها و ساختارهای داده.
- اعتبارسنجی ورودی‌ها.
- احراز هویت.
- مجوزدهی و کنترل دسترسی.
- سرویس‌های خارجی مانند پیامک.
- گزارش‌گیری و خروجی گرفتن.
- مدیریت تنظیمات.
- ثبت رویدادها و گزارش‌های امنیتی.
- تست‌ها و ابزارهای توسعه.

هر قابلیت مهم باید در یک ماژول مشخص قرار بگیرد و ارتباط آن با سایر ماژول‌ها از طریق رابط‌های مشخص انجام شود.

منطق تجاری را مستقیماً داخل فایل‌های رابط کاربری یا کنترلرهای بزرگ قرار نده.

از ایجاد فایل‌های بسیار بزرگ، تکرار منطق در چند قسمت و وابستگی‌های دوری بین ماژول‌ها خودداری کن.

افزودن قابلیت جدید یا تغییر یک بخش نباید بدون ضرورت باعث بازنویسی سایر بخش‌ها شود.

ماژول‌ها باید دارای ساختار مشخص، وابستگی‌های شفاف، تنظیمات مستقل و امکان توسعه و تست جداگانه باشند.

۲. مهم‌ترین الزام پروژه: نصب روی cPanel بدون SSH

این مورد یک الزام قطعی است و باید از ابتدای طراحی رعایت شود.

می‌خواهم نرم‌افزار روی هاست اشتراکی cPanel نصب شود و مدیر سیستم بتواند آن را بدون اتصال SSH و بدون اجرای دستی دستورات ترمینال راه‌اندازی کند.

برای این منظور، سامانه باید شرایط زیر را داشته باشد:

۱. امکان بارگذاری فایل‌های پروژه از طریق File Manager سی‌پنل.

۲. امکان تنظیم برنامه Node.js از طریق رابط گرافیکی cPanel، مشروط به اینکه سرویس میزبانی از اجرای برنامه Node.js پشتیبانی کند.

۳. امکان تنظیم متغیرهای محیطی و اطلاعات اتصال پایگاه داده از طریق رابط مدیریتی هاست.

۴. آماده‌سازی فایل‌های فرانت‌اند و خروجی تولید مناسب برای محیط عملیاتی، به‌گونه‌ای که هنگام نصب روی هاست نیازی به اجرای ابزارهای build وجود نداشته باشد.

۵. ارائه وابستگی‌های لازم به شکلی که نصب آن‌ها از طریق امکانات گرافیکی موجود در هاست امکان‌پذیر باشد. در صورت نیاز به نصب npm dependencies، مسیر نصب بدون SSH را مشخص کن و روش جایگزین معتبر ارائه بده.

۶. امکان ایجاد جداول، روابط، ایندکس‌ها و اطلاعات اولیه پایگاه داده از طریق یک فرایند نصب تحت وب یا روش گرافیکی مستند و ایمن.

۷. ارائه فایل SQL مستقل برای نصب یا بازیابی پایگاه داده، در صورتی که این روش برای محیط مقصد مناسب‌تر باشد.

۸. امکان ساخت حساب مدیر اصلی در نخستین راه‌اندازی.

۹. ارائه راهنمای فارسی نصب، به‌روزرسانی، پشتیبان‌گیری، بازیابی و عیب‌یابی.

۱۰. امکان بررسی سازگاری محیط هاست پیش از نصب.

۱۱. نمایش خطاهای نصب به زبان قابل فهم، بدون افشای اطلاعات حساس یا جزئیات داخلی سرور.

۱۲. امکان اجرای migrationهای نسخه‌های جدید به روشی امن و قابل پیگیری.

۱۳. جلوگیری از نصب مجدد ناخواسته یا دسترسی غیرمجاز به ابزار نصب پس از راه‌اندازی.

۱۴. ذخیره اطلاعات محرمانه در متغیرهای محیطی یا محل امن خارج از مسیر عمومی وب، تا حد امکان مطابق امکانات هاست.

۱۵. ارائه ابزار بررسی سلامت نرم‌افزار شامل وضعیت اتصال پایگاه داده، نسخه Node.js، وضعیت ماژول‌ها و خطاهای مهم.

فرایند نصب باید برای کاربری که با برنامه‌نویسی و SSH آشنایی ندارد نیز قابل انجام باشد.

**محدودیت مهم:** اگر ارائه‌دهنده هاست امکان اجرای برنامه Node.js، تعیین نقطه ورود برنامه یا نصب وابستگی‌های آن بدون SSH را نداشته باشد، این نیاز از طریق کدنویسی به‌تنهایی قابل تضمین نیست. در چنین شرایطی، محدودیت را دقیق توضیح بده و از ادعای سازگاری غیرواقعی خودداری کن.

۴. مدیریت کاربران و نقش‌ها

یک سیستم مدیریت کاربران حرفه‌ای ایجاد کن.

انواع کاربران می‌توانند شامل موارد زیر باشند:

- مدیر اصلی سامانه.
- مدیر اجرایی مؤسسه.
- مدیر آموزش.
- کارمند ثبت‌نام.
- کارمند مالی.
- مسئول حضور و غیاب.
- استاد.
- دانشجو یا دانش‌آموز.
- سایر کاربران با نقش‌های سفارشی.

این فهرست نباید ثابت و غیرقابل توسعه باشد.

مدیر مجاز باید بتواند نقش‌های جدید تعریف کند و مجوزهای موردنیاز را به آن‌ها اختصاص دهد.

مدیریت نقش‌ها و سطح دسترسی

یک سیستم Role-Based Access Control یا RBAC حرفه‌ای پیاده‌سازی کن.

مدیر باید بتواند:

- نقش جدید ایجاد کند.
- نقش‌ها را ویرایش کند.
- نقش‌های غیرقابل حذف یا ضروری را مدیریت‌شده نگه دارد.
- نقش‌های غیرضروری را حذف یا غیرفعال کند.
- مجوزهای هر نقش را انتخاب کند.
- نقش مشخصی را به هر کاربر اختصاص دهد.
- کاربران دارای یک نقش مشخص را مشاهده کند.
- دسترسی‌های هر نقش را بررسی کند.
- از تخصیص ناخواسته مجوزهای مدیریتی به کاربران عادی جلوگیری کند.

مجوزها باید تا حد امکان براساس ماژول، منبع و عملیات تعریف شوند.

برای نمونه:

- مشاهده اطلاعات.
- ایجاد رکورد.
- ویرایش.
- حذف.
- تأیید یا رد.
- ثبت پرداخت.
- تأیید پرداخت.
- صدور مدرک.
- لغو مدرک.
- مشاهده گزارش.
- خروجی گرفتن.
- مدیریت تنظیمات.

برای هر عملیات حساس، مجوز مستقل تعریف کن.

صرفاً مخفی‌کردن دکمه‌ها در رابط کاربری کافی نیست؛ مجوز هر درخواست باید در سمت سرور نیز کنترل شود.

سیستم باید از اصل حداقل دسترسی پیروی کند.

تغییر نقش کاربر باید بلافاصله در مجوزهای جدید او مؤثر باشد.

همچنین باید امکان فعال یا غیرفعال‌کردن حساب، تغییر رمز عبور، بازنشانی امن رمز، خروج از نشست‌های فعال در صورت نیاز و مشاهده سوابق امنیتی کاربر وجود داشته باشد.

۵. کنترل دسترسی در سطح کلاس و داده‌ها

این بخش یکی از مهم‌ترین بخش‌های سامانه است.

هر استاد فقط باید به کلاس‌هایی دسترسی داشته باشد که به او تخصیص داده شده‌اند.

هر دانشجو فقط باید اطلاعات شخصی، ثبت‌نام‌ها، برنامه کلاس‌ها، وضعیت حضور و غیاب، پرداخت‌ها و مدارک متعلق به خودش را مشاهده کند؛ مگر آنکه مجوز مشخص دیگری به‌صورت آگاهانه تعریف شده باشد.

کاربر نباید با تغییر شناسه رکورد در آدرس، درخواست API یا فرم‌ها بتواند به اطلاعات دیگران دسترسی پیدا کند.

برای هر درخواست باید مالکیت داده، عضویت در کلاس و مجوز کاربر بررسی شود.

نمونه الزامات:

- استاد کلاس A نتواند اطلاعات کلاس B را مشاهده یا ویرایش کند، مگر اینکه به آن دسترسی داشته باشد.
- استاد نتواند فهرست کامل دانشجویان مؤسسه را بدون مجوز مشاهده کند.
- دانشجوی کلاس A نتواند اطلاعات خصوصی دانشجوی کلاس B را مشاهده کند.
- دانشجو نتواند اطلاعات مالی یا حضور و غیاب سایر دانشجویان را دریافت کند.
- کارمند ثبت‌نام نتواند تنظیمات امنیتی یا مالی غیرمجاز را تغییر دهد.
- کارمند مالی نتواند مجوزهای مدیریتی خود را افزایش دهد.
- APIهای خروجی اطلاعات نیز باید همین محدودیت‌ها را رعایت کنند.

این کنترل‌ها باید در سطح سرویس‌ها و دسترسی به داده‌ها نیز اعمال شوند، نه فقط در رابط کاربری.

برای این بخش تست‌های اختصاصی بنویس و دسترسی غیرمجاز را در آزمون‌های خود بررسی کن.

- نمایش قوانین ثبت‌نام.
- اعلام وضعیت درخواست.
- ثبت تاریخ ارسال.
- تخصیص کد پیگیری.
- جلوگیری از ثبت‌های تکراری نامعتبر.

در طراحی فرم عمومی، اطلاعات غیرضروری را درخواست نکن و اطلاعات خصوصی را به کاربران غیرمجاز نمایش نده.

استاد تنها باید بتواند حضور و غیاب کلاس‌های مجاز خود را ثبت یا مشاهده کند.

تغییرات مهم حضور و غیاب باید در گزارش رویدادها ذخیره شوند.

۱۱. مدیریت شهریه، پرداخت و اقساط

هر تراکنش یا پرداخت دستی باید دارای شناسه یکتا و سابقه تغییرات باشد.

اسناد مالی

صفحه اعتبارسنجی باید فقط اطلاعات ضروری برای بررسی اعتبار مدرک را نمایش دهد.

اطلاعات خصوصی فراگیر نباید از طریق این صفحه افشا شود.

لغو یا بی‌اعتبارشدن مدرک باید در صفحه اعتبارسنجی منعکس شود.

۱۳. اتصال کامل به پنل پیامکی IPPanel

اتصال پیامکی باید مطابق مستندات رسمی IPPanel Edge API پیاده‌سازی شود.

مستندات مرجع:

https://ippanelcom.github.io/Edge-Document/docs/

آدرس پایه API طبق مستندات:

https://edge.ippanel.com/v1

از مستندات رسمی برای احراز هویت، ارسال پیامک، ارسال با پترن، بررسی وضعیت پیامک و سایر عملیات موردنیاز استفاده کن.

مسیرها، ساختار درخواست‌ها، نام پارامترها، قالب پاسخ‌ها و روش احراز هویت را حدس نزن.

پیش از پیاده‌سازی هر عملیات، مستندات همان عملیات را بررسی کن.

در صورت استفاده از API Key، آن را فقط در سمت سرور نگه دار و از قرارگرفتن آن در کد فرانت‌اند، فایل‌های عمومی، لاگ‌ها یا پاسخ‌های API جلوگیری کن.

معماری ماژول پیامک

ماژول پیامک باید مستقل باشد تا در آینده بتوان ارائه‌دهنده پیامک دیگری را نیز اضافه کرد.

برای IPPanel یک Adapter مستقل با رابط مشخص تعریف کن.

این ماژول باید قابلیت‌های زیر را داشته باشد:

- ثبت تنظیمات اتصال.
- ثبت امن API Key.
- تعیین شناسه یا اطلاعات فرستنده، در صورت نیاز API.
- بررسی اتصال با ارائه‌دهنده.
- مدیریت خطاهای ارتباطی.
- ثبت درخواست‌ها و نتایج ارسال بدون ذخیره اطلاعات محرمانه.
- نگهداری شناسه ارسال.
- پیگیری وضعیت ارسال در صورت پشتیبانی API.
- نمایش سابقه پیامک‌ها.
- جست‌وجو براساس شماره مقصد، نوع پیام، تاریخ و وضعیت.
- امکان ارسال آزمایشی برای مدیر مجاز.
- امکان فعال یا غیرفعال‌کردن هر دسته از پیامک‌ها.
- جلوگیری از ارسال ناخواسته پیامک تکراری.
- مدیریت خطا و تلاش مجدد کنترل‌شده.
- محدودیت تعداد ارسال برای جلوگیری از سوءاستفاده.

هیچ پیامکی صرفاً به دلیل ثبت یک رویداد نباید بدون کنترل مناسب چند بار ارسال شود.

مدیریت پترن‌های پیامکی

سامانه باید از پیامک‌های الگومحور IPPanel پشتیبانی کند.

برای هر نوع رویداد، امکان تعریف پترن مستقل وجود داشته باشد.

نمونه رویدادها:

۱. دریافت درخواست پیش‌ثبت‌نام. ۲. تأیید پیش‌ثبت‌نام. ۳. رد درخواست ثبت‌نام. ۴. نهایی‌شدن ثبت‌نام. ۵. اعلام اطلاعات کلاس. ۶. تغییر برنامه کلاس. ۷. یادآوری شروع کلاس. ۸. اطلاع‌رسانی غیبت، طبق سیاست مؤسسه. ۹. یادآوری سررسید قسط. ۱۰. اطلاع‌رسانی پرداخت موفق. ۱۱. اعلام تأیید یا رد رسید کارت‌به‌کارت. ۱۲. اطلاع‌رسانی آماده‌شدن مدرک. ۱۳. اطلاع‌رسانی‌های مدیریتی. ۱۴. سایر رویدادهای قابل افزودن در آینده.

این فهرست باید از طریق معماری ماژولار قابل توسعه باشد.

تنظیم متغیرهای هر پترن

یکی از الزامات اصلی پروژه این است که متغیرهای ارسالی برای هر پترن قابل تنظیم باشند.

برای هر رویداد باید بتوان موارد زیر را تعیین کرد:

- عنوان رویداد.
- فعال یا غیرفعال‌بودن ارسال.
- کد پترن مربوط در IPPanel.
- نوع پیامک.
- متغیرهای موردنیاز پترن.
- منبع استخراج هر متغیر از اطلاعات سامانه.
- مقدار پیش‌فرض مجاز، در صورت نیاز.
- شرایط اجرای ارسال.
- مخاطب مجاز ارسال.
- زمان‌بندی یا تأخیر ارسال در صورت پشتیبانی معماری.
- سیاست تلاش مجدد.
- توضیحات مدیریتی.
- تنظیمات مخصوص همان نوع پیامک.

برای نمونه، مدیر بتواند تعیین کند متغیر نام دانشجو از پرونده فراگیر، عنوان کلاس از اطلاعات کلاس و مبلغ قسط از اطلاعات مالی استخراج شود.

نام متغیرهای داخلی سامانه را با نام متغیرهایی که پترن IPPanel انتظار دارد یکسان فرض نکن.

یک لایه Mapping مستقل ایجاد کن تا بتوان نام متغیر داخلی را به نام متغیر موردنیاز هر پترن نگاشت کرد.

ساختار متغیرها و کد پترن نباید به‌صورت پراکنده و ثابت در کدهای مختلف نوشته شوند.

در پنل مدیریت، رابطی برای تعریف و ویرایش نگاشت متغیرها ایجاد کن.

سامانه باید پیش از ارسال بررسی کند که متغیرهای ضروری پترن موجود هستند و مقدار معتبر دارند.

اگر متغیر ضروری وجود نداشت، پیامک ارسال نشود و خطای قابل فهم ثبت شود.

صف ارسال و گزارش پیامک

برای ارسال انبوه یا رویدادهای متعدد، معماری صف قابل اتکا طراحی کن که با محدودیت‌های هاست اشتراکی سازگار باشد.

در صورت نیاز به پردازش زمان‌بندی‌شده، امکان تنظیم آن از طریق Cron Jobs گرافیکی cPanel را بررسی کن.

اگر پردازش زمان‌بندی‌شده در هاست مقصد ممکن نبود، محدودیت آن را مستند کن و به قابلیت‌های غیرقابل اتکای درخواست‌های تصادفی وب وابسته نشو.

وضعیت‌های پیامک، خطاهای ارتباطی و نتایج پیگیری باید قابل مشاهده باشند.

گزارش پیامک‌ها را از اطلاعات اصلی دانشجویان و رویدادهای آموزشی جدا نگه دار، اما ارتباط آن‌ها با رویداد مربوط را از طریق شناسه‌های داخلی حفظ کن.

۱۴. تنظیمات جامع سامانه

یک ماژول تنظیمات مرکزی و حرفه‌ای بساز.

هدف این است که مدیر مجاز برای تغییر رفتار معمول نرم‌افزار مجبور به ویرایش مستقیم کد نباشد.

تنظیمات باید دسته‌بندی‌شده باشند.

دسته‌های پیشنهادی:

تنظیمات عمومی

نام مؤسسه، لوگو، اطلاعات تماس، زبان، منطقه زمانی و قالب‌های پیش‌فرض.

تنظیمات ظاهری

رنگ‌ها، لوگو، عنوان صفحات، اجزای هویت بصری و تنظیمات داشبورد.

تنظیمات تاریخ و زمان

نوع تقویم نمایشی، منطقه زمانی، قالب تاریخ، قالب ساعت و نمایش اعداد.

تنظیمات ثبت‌نام

فیلدهای فرم‌ها، شرایط پذیرش، محدودیت ظرفیت، وضعیت پیش‌فرض و سیاست‌های ثبت‌نام.

تنظیمات کلاس‌ها

وضعیت‌های کلاس، محدودیت‌های زمانی، سیاست‌های برگزاری و تنظیمات عمومی جلسات.

تنظیمات حضور و غیاب

انواع وضعیت‌ها، حد مجاز غیبت، سیاست تأخیر و مجوزهای اصلاح.

تنظیمات مالی

واحد پول، قالب نمایش مبلغ، روش‌های پرداخت، تنظیمات اقساط و سیاست تأیید پرداخت.

تنظیمات مدارک

قالب‌های مدرک، متن پیش‌فرض، شرایط صدور، امضاها و تنظیمات اعتبارسنجی.

تنظیمات پیامک

اطلاعات اتصال IPPanel، پترن‌ها، نگاشت متغیرها، رویدادها، محدودیت ارسال و گزارش‌ها.

تنظیمات امنیت

سیاست رمز عبور، نشست‌ها، محدودیت ورود، مجوزها و تنظیمات امنیتی قابل پشتیبانی.

تنظیمات کاربران

قواعد ساخت حساب، فعال‌سازی حساب، نقش‌های پیش‌فرض و سیاست‌های مدیریت کاربران.

تنظیمات اعلان‌ها

فعال‌سازی یا غیرفعال‌سازی اعلان‌ها و انتخاب رویدادهای قابل اطلاع‌رسانی.

تنظیمات فایل‌ها

حداکثر اندازه فایل، پسوندهای مجاز و سیاست نگهداری فایل‌ها.

تنظیمات پشتیبان‌گیری

ایجاد نسخه پشتیبان، مشاهده تاریخچه، بازیابی و تنظیمات مربوط به نگهداری نسخه‌ها.

تنظیمات سامانه

وضعیت ماژول‌ها، بررسی سلامت، اطلاعات نسخه و گزارش خطاهای ضروری.

تنظیمات حساس باید فقط در اختیار نقش‌های مجاز باشند.

اطلاعاتی مانند API Key باید هنگام نمایش ماسک شوند.

هر تغییر حساس باید در صورت امکان ثبت رویداد شود.

از ایجاد یک جدول تنظیمات بدون اعتبارسنجی که تمام نوع داده‌ها را به‌صورت نامحدود و ناامن ذخیره کند، خودداری کن.

تنظیمات باید دارای نوع داده، اعتبارسنجی، مقدار پیش‌فرض، محدوده دسترسی و رفتار مشخص باشند.

۱۵. داشبورد حرفه‌ای و گزارش‌های مدیریتی

یک داشبورد کاربردی و سطح بالا برای مدیریت مؤسسه طراحی کن.

داشبورد باید علاوه بر زیبایی، اطلاعات قابل استفاده برای تصمیم‌گیری ارائه کند.

محتوا باید براساس نقش کاربر تغییر کند.

شاخص‌های پیشنهادی

- تعداد کل فراگیران.
- تعداد فراگیران فعال.
- تعداد اساتید فعال.
- تعداد کلاس‌های در حال ثبت‌نام.
- تعداد کلاس‌های در حال برگزاری.
- تعداد کلاس‌های پایان‌یافته.
- تعداد درخواست‌های پیش‌ثبت‌نام.
- تعداد درخواست‌های در انتظار بررسی.
- تعداد جلسات امروز.
- آمار حضور و غیاب.
- مجموع شهریه‌های ثبت‌شده.
- مجموع دریافتی‌ها.
- مانده مطالبات.
- اقساط سررسیدشده.
- پرداخت‌های در انتظار تأیید.
- تعداد مدارک صادرشده.
- وضعیت پیامک‌های ارسال‌شده.
- خطاهای مهم سیستم، فقط برای مدیران مجاز.

این شاخص‌ها باید از داده‌های واقعی پایگاه داده محاسبه شوند.

اعداد ثابت یا نمودارهای نمایشی غیرمرتبط با داده‌های واقعی ایجاد نکن.

نمودارها

براساس داده‌های موجود، نمودارهای کاربردی ایجاد کن.

برای مثال:

- روند ثبت‌نام در بازه‌های زمانی.
- مقایسه ثبت‌نام کلاس‌ها.
- روند درآمد و دریافت‌ها.
- توزیع وضعیت پرداخت‌ها.
- آمار حضور و غیاب.
- مقایسه ظرفیت و ثبت‌نام کلاس‌ها.
- عملکرد آموزشی در بازه انتخابی.
- آمار پیامک‌ها و وضعیت ارسال.

امکانات زیر را در صورت تناسب با هر نمودار فراهم کن:

- فیلتر زمانی.
- فیلتر کلاس.
- مقایسه دوره‌ها.
- نمایش جزئیات با انتخاب بخش نمودار.
- به‌روزرسانی داده‌ها.
- خروجی گرفتن از گزارش.

نمودارها نباید صرفاً برای تزئین باشند؛ هرکدام باید هدف مشخصی داشته باشند.

۱۶. طراحی رابط کاربری و تجربه کاربری

رابط کاربری باید مدرن، حرفه‌ای، خلوت، چشم‌نواز و مناسب استفاده روزانه باشد.

از طراحی‌های قدیمی، شلوغ، پر از رنگ‌های نامرتبط و داشبوردهای متراکم اجتناب کن.

الزامات طراحی

- زبان رابط کاربری فارسی.
- راست‌چین واقعی و کامل.
- پشتیبانی درست از متن‌های RTL.
- طراحی واکنش‌گرا برای موبایل، تبلت و دسکتاپ.
- ناوبری مشخص و قابل فهم.
- منوی کناری قابل جمع‌شدن.
- سربرگ حرفه‌ای.
- نوار جست‌وجو در بخش‌های مناسب.
- جدول‌های پیشرفته با فیلتر، مرتب‌سازی و صفحه‌بندی.
- فرم‌های گروه‌بندی‌شده و قابل فهم.
- نمایش خطا در کنار فیلد مربوط.
- پیام موفقیت و هشدار واضح.
- صفحات خالی با راهنمای اقدام بعدی.
- تأیید عملیات حساس مانند حذف، لغو مدرک یا تأیید پرداخت.
- طراحی مناسب چاپ برای مدارک و اسناد مالی.
- رعایت اصول دسترس‌پذیری و کنتراست.
- حفظ سرعت رابط کاربری در هاست اشتراکی.

یک Design System مشترک ایجاد کن تا رنگ‌ها، فاصله‌ها، اندازه‌ها، دکمه‌ها، فرم‌ها، جدول‌ها، پنجره‌های محاوره‌ای و اجزای تکرارشونده ظاهر یکپارچه داشته باشند.

از کامپوننت‌های مشترک برای عناصر تکرارشونده استفاده کن.

از ایجاد صفحات متعدد با ظاهر و رفتار متفاوت خودداری کن.

رابط فارسی

در تبدیل تاریخ، نمایش اعداد و ورودی‌های فارسی دقت کن.

نمایش تاریخ در رابط کاربری باید از تقویم شمسی پشتیبانی کند.

اطلاعات تاریخ در پایگاه داده باید با یک سیاست زمانی روشن ذخیره شوند و تبدیل تاریخ صرفاً در لایه نمایش انجام نشود.

تاریخ‌های جلسات، ثبت‌نام‌ها، پرداخت‌ها، اقساط و مدارک باید در محاسبات و مرتب‌سازی دچار اختلال نشوند.

برای تاریخ‌های شمسی، سال کبیسه و موارد مرزی تقویم تست بنویس.

تبدیل ارقام فارسی و عربی در شماره تلفن‌ها، مبالغ و فیلدهای عددی باید کنترل‌شده باشد.

ورودی‌های شماره تلفن باید پیش از ذخیره‌سازی به قالب استاندارد مورد انتظار سیستم تبدیل شوند.

۱۷. امنیت حرفه‌ای

امنیت سامانه باید از ابتدا در معماری پیاده‌سازی شود.

صرفاً افزودن یک صفحه ورود به‌معنای ایمن‌بودن پروژه نیست.

حداقل موارد زیر باید رعایت شوند:

- هش امن رمزهای عبور با الگوریتم مناسب.
- مدیریت امن نشست‌ها.
- تنظیم کوکی‌های امن در محیط HTTPS.
- محافظت در برابر حملات CSRF در مسیرهای مربوط.
- اعتبارسنجی ورودی سمت سرور.
- جلوگیری از SQL Injection با پرس‌وجوهای پارامتری یا ابزار معتبر.
- جلوگیری از XSS با اعتبارسنجی و خروجی‌گذاری امن.
- استفاده از تنظیمات امنیتی مناسب HTTP.
- محدودیت نرخ درخواست برای ورود و عملیات حساس.
- جلوگیری از آزمون نامحدود رمز عبور.
- بررسی مالکیت داده‌ها و مقابله با IDOR.
- کنترل مجوزها در تمام مسیرهای حساس API.
- مدیریت امن بازیابی رمز عبور.
- جلوگیری از افشای اطلاعات از طریق خطاها.
- نگهداری امن کلیدهای API و اطلاعات اتصال.
- اعتبارسنجی فایل‌های بارگذاری‌شده.
- جلوگیری از اجرای فایل‌های بارگذاری‌شده.
- محدودکردن دسترسی مستقیم به فایل‌های خصوصی.
- ثبت رخدادهای مهم امنیتی.
- محافظت از مسیرهای مدیریتی.
- جلوگیری از افزایش غیرمجاز سطح دسترسی.
- کنترل وضعیت حساب در زمان احراز هویت.
- مدیریت نشست‌های منقضی‌شده.
- بررسی وضعیت مالکیت و اعتبار فایل‌ها هنگام دانلود.
- جلوگیری از دست‌کاری مبلغ، وضعیت پرداخت و مالکیت مدارک از طریق درخواست‌های دست‌کاری‌شده.

هیچ رمز عبور، کلید محرمانه، توکن یا اطلاعات حساس نباید داخل مخزن کد یا فایل‌های قابل دسترسی عمومی قرار گیرد.

اگر امکان استفاده از MFA وجود دارد، آن را به‌صورت ماژولار و قابل تنظیم طراحی کن.

برای فایل‌های محرمانه، مانند رسید پرداخت و اسناد هویتی، دسترسی باید از طریق مسیر کنترل‌شده سمت سرور انجام شود.

هیچ فایل خصوصی نباید صرفاً با دانستن نام یا مسیر آن قابل دانلود باشد.

ثبت رویدادها و حسابرسی

برای عملیات حساس گزارش حسابرسی ایجاد کن.

نمونه رویدادها:

- ورود موفق و ناموفق.
- تغییر نقش.
- تغییر تنظیمات امنیتی.
- تغییر مجوزها.
- تأیید یا رد پرداخت.
- اصلاح حضور و غیاب.
- صدور یا لغو مدرک.
- حذف یا غیرفعال‌سازی رکوردهای مهم.
- تغییر تنظیمات IPPanel.
- تغییر تنظیمات مؤسسه.

گزارش‌ها باید دارای زمان، شناسه کاربر، نوع عملیات، موجودیت مربوط و اطلاعات لازم برای بررسی باشند.

رمزهای عبور، API Keyها و اطلاعات محرمانه نباید در گزارش‌ها ثبت شوند.

از ذخیره اطلاعات غیرضروری و حساس در لاگ‌ها خودداری کن.

برای حذف اطلاعات، سیاست روشن و متناسبی در نظر بگیر تا سوابق مالی و آموزشی ضروری به‌صورت ناخواسته از بین نروند.

۱۸. طراحی پایگاه داده

پایگاه داده باید اصولی، امن و توسعه‌پذیر باشد.

موجودیت‌های اصلی را براساس نیاز پروژه طراحی کن؛ از جمله:

- کاربران.
- نقش‌ها.
- مجوزها.
- ارتباط نقش و مجوز.
- ارتباط کاربر و نقش.
- پروفایل فراگیران.
- پروفایل اساتید.
- دوره‌ها.
- کلاس‌ها.
- استادان تخصیص‌یافته به کلاس‌ها.
- جلسات کلاس.
- ثبت‌نام‌ها.
- درخواست‌های پیش‌ثبت‌نام.
- سوابق حضور و غیاب.
- شهریه‌ها و صورتحساب‌ها.
- برنامه اقساط.
- پرداخت‌ها.
- رسیدها.
- قالب‌های مدارک.
- مدارک صادرشده.
- پترن‌ها و تنظیمات پیامک.
- نگاشت متغیرهای پیامک.
- صف ارسال پیامک.
- گزارش ارسال پیامک.
- تنظیمات سامانه.
- رویدادهای حسابرسی.
- فایل‌های مرتبط.
- ساختارهای لازم برای افزونه‌ها و ماژول‌های آینده.

این فهرست صرفاً نقطه شروع است؛ ساختار نهایی را براساس روابط واقعی سیستم طراحی کن.

قواعد زیر الزامی هستند:

- استفاده از کلیدهای اصلی و خارجی مناسب.
- تعریف روابط روشن.
- تعریف ایندکس روی فیلدهای جست‌وجو و ارتباطات پرتکرار.
- محدودیت‌های یکتا برای اطلاعاتی که باید یکتا باشند.
- جلوگیری از رکوردهای تکراری نامعتبر.
- استفاده از تراکنش در عملیات چندمرحله‌ای حساس.
- یکپارچگی اطلاعات مالی.
- حفظ روابط تاریخی ثبت‌نام و کلاس.
- مدیریت صحیح تاریخ و زمان.
- امکان migration نسخه‌های جدید.
- امکان تهیه نسخه پشتیبان و بازیابی.
- جلوگیری از حذف آبشاری ناخواسته اطلاعات مهم.

از ذخیره همه اطلاعات در یک جدول بزرگ یا نگهداری اطلاعات مرتبط به‌شکل رشته‌های JSON نامحدود بدون دلیل معماری خودداری کن.

برای روابط پیچیده، طراحی ERD و مستندات پایگاه داده تهیه کن.

قبل از نهایی‌سازی ساختار، سناریوهای ثبت‌نام، پرداخت، حضور و غیاب، صدور مدرک و لغو عملیات را بررسی کن.

۱۹. مدیریت فایل‌ها و اسناد

سامانه باید امکان بارگذاری و مدیریت فایل‌های مرتبط را فراهم کند.

برای مثال:

- تصویر پروفایل.
- مدارک ثبت‌نام.
- رسیدهای پرداخت.
- فایل‌های مرتبط با کلاس.
- تصاویر و فایل‌های قالب مدرک.
- امضا و مهر مؤسسه.

قابلیت‌ها:

- اعتبارسنجی نوع واقعی فایل.
- محدودیت اندازه.
- نام‌گذاری امن.
- جلوگیری از Path Traversal.
- جلوگیری از اجرای فایل.
- تعیین سطح دسترسی دانلود.
- ثبت مالکیت فایل.
- حذف و جایگزینی کنترل‌شده.
- ثبت ارتباط فایل با موجودیت مربوط.
- جلوگیری از نمایش عمومی فایل‌های خصوصی.
- نمایش خطای واضح هنگام بارگذاری ناموفق.

مسیر ذخیره‌سازی باید قابل تنظیم باشد.

در محیط cPanel، روش ذخیره‌سازی باید با محدودیت فضای هاست و دسترسی‌های موجود سازگار باشد.

امکان تهیه پشتیبان از فایل‌ها و اطلاعات مرتبط با پایگاه داده را در نظر بگیر.

۲۰. جست‌وجو، گزارش‌گیری و خروجی

در بخش‌های مدیریتی، جست‌وجو و فیلتر متناسب با نوع داده وجود داشته باشد.

برای مثال:

- جست‌وجوی فراگیران با نام، شماره همراه و کد.
- فیلتر کلاس براساس وضعیت، استاد و تاریخ.
- فیلتر ثبت‌نام براساس وضعیت درخواست.
- گزارش پرداخت براساس تاریخ، روش پرداخت و وضعیت.
- گزارش اقساط معوق.
- گزارش حضور و غیاب.
- گزارش مدارک صادرشده.
- گزارش پیامک‌ها.
- گزارش عملکرد کاربران دارای مجوز مربوط.

خروجی‌های CSV و PDF را در بخش‌های مناسب پشتیبانی کن.

فایل‌های خروجی نیز مشمول محدودیت دسترسی باشند.

در خروجی CSV مراقب Formula Injection باش.

برای گزارش‌های حجیم، از دریافت یک‌جای تمام داده‌ها بدون صفحه‌بندی یا محدودیت مناسب خودداری کن.

۲۱. مدیریت ماژول‌ها و توسعه آینده

پروژه باید قابلیت رشد داشته باشد.

یک ساختار مشخص برای شناسایی و مدیریت ماژول‌ها تعریف کن.

هر ماژول باید دارای مشخصات روشنی مانند موارد زیر باشد:

- شناسه.
- نام.
- نسخه.
- وضعیت فعال‌بودن.
- وابستگی‌ها.
- تنظیمات.
- مجوزهای موردنیاز.
- مسیرهای مربوط.
- سرویس‌های ارائه‌شده.
- جدول‌ها یا تغییرات پایگاه داده مرتبط.
- قابلیت‌های رابط کاربری.

در صورت امکان، یک صفحه مدیریتی برای مشاهده وضعیت ماژول‌ها ایجاد کن.

ماژول‌هایی مانند SMS، مدیریت مالی، مدارک و گزارش‌های پیشرفته باید از نظر ساختار نرم‌افزاری به‌درستی تفکیک شوند.

غیرفعال‌کردن ماژول نباید باعث خرابی ماژول‌های وابسته شود.

پیش از غیرفعال‌سازی یا حذف، وابستگی‌ها و اطلاعات تحت تأثیر بررسی شوند.

هیچ ماژولی نباید با خاموش‌کردن رابط کاربری از پایگاه داده یا سرویس‌ها جدا شود، در حالی که مسیرهای حساس آن همچنان بدون کنترل قابل دسترسی باشند.

برای اضافه‌شدن قابلیت‌های جدید، رابط‌های توسعه مشخص و مستندات داخلی فراهم کن.

۲۲. عملکرد و پایداری

نرم‌افزار برای محیط هاست اشتراکی طراحی می‌شود.

بنابراین باید مصرف منابع آن کنترل‌شده باشد.

الزامات:

- صفحه‌بندی سمت سرور.
- بهینه‌سازی پرس‌وجوهای پایگاه داده.
- جلوگیری از N+1 Query.
- بارگذاری فقط اطلاعات موردنیاز هر صفحه.
- ایندکس‌گذاری مناسب.
- محدودکردن گزارش‌های سنگین.
- مدیریت خطاهای ارتباط با پایگاه داده.
- مدیریت صحیح خطاهای API خارجی.
- جلوگیری از پردازش‌های تکراری.
- محدودکردن اندازه درخواست‌ها.
- مدیریت مناسب فایل‌های استاتیک.
- استفاده از cache فقط در مواردی که سازگاری آن با معماری روشن است.
- ثبت و بررسی خطاهای عملیاتی مهم.
- جلوگیری از وابستگی غیرضروری به سرویس‌های خارجی برای عملکرد اصلی سامانه.

نباید برای ساده‌ترشدن پیاده‌سازی، همه اطلاعات پایگاه داده در حافظه بارگذاری شوند.

اگر عملیات زمان‌بر مانند ارسال انبوه پیامک یا تولید تعداد زیادی مدرک وجود دارد، روش پردازش مرحله‌ای متناسب با محدودیت‌های محیط انتخاب کن.

۲۳. پشتیبان‌گیری و بازیابی

یک بخش مدیریتی برای پشتیبان‌گیری ایجاد کن.

در صورت سازگاری با امکانات هاست، قابلیت‌های زیر را فراهم کن:

- ثبت تاریخ و وضعیت پشتیبان‌گیری.
- نمایش فهرست نسخه‌های موجود.
- محدودیت دسترسی به فایل‌های پشتیبان.
- تشخیص خطای تهیه نسخه پشتیبان.
- راهنمای بازیابی.
- کنترل سازگاری نسخه پشتیبان پیش از بازیابی، تا حد امکان.
- ثبت رویداد بازیابی اطلاعات.

مسیر ذخیره‌سازی نسخه‌های پشتیبان باید امن باشد.

در صورت محدودیت هاست برای فشرده‌سازی، زمان اجرا یا فضای ذخیره‌سازی، محدودیت را توضیح بده و روش جایگزین سازگار پیشنهاد کن.

عملیات بازیابی باید فقط در اختیار مدیران دارای مجوز ویژه باشد و پیش از اجرا هشدار واضح نمایش دهد.

در صورت امکان، ZIP نهایی را نیز ایجاد کن و ساختار آن را بررسی کن.

۲۹. قواعد قطعی اجرای پروژه

قواعد زیر باید در تمام مراحل رعایت شوند:

**قاعده اول:** به‌جای توضیح طولانی درباره اینکه چه کاری باید انجام شود، خود کار را انجام بده.

**قاعده دوم:** قبل از کدنویسی، معماری و ساختار فایل‌ها را مشخص کن، اما برای شروع پیاده‌سازی منتظر تأیید من نمان.

**قاعده سوم:** قابلیت‌ها باید واقعاً کار کنند. دکمه نمایشی، نمودار ساختگی، فرم بدون ذخیره‌سازی، API صوری و صفحه‌ای که فقط ظاهر مناسبی دارد قابل قبول نیست.

**قاعده چهارم:** هیچ قابلیت اصلی را صرفاً با TODO، داده ثابت، Mock یا پیام «به‌زودی» جایگزین نکن.

**قاعده پنجم:** اگر بخشی به اطلاعاتی مانند کلید API، اطلاعات حساب پیامکی یا تنظیمات اختصاصی هاست نیاز دارد، صفحه تنظیمات و اعتبارسنجی آن را ایجاد کن. نبود این اطلاعات نباید مانع پیاده‌سازی ساختار واقعی آن بخش شود.

**قاعده ششم:** هیچ عملیات حساس یا اطلاعات محرمانه‌ای را فقط با کنترل فرانت‌اند محافظت نکن.

**قاعده هفتم:** سازگاری با cPanel را با درنظرگرفتن محدودیت‌های واقعی آن پیاده‌سازی کن. وجود یک فایل ZIP به‌تنهایی به‌معنای قابل نصب بودن نرم‌افزار نیست.

**قاعده هشتم:** هر بخش باید با داده‌ها و بخش‌های مرتبط ارتباط واقعی داشته باشد. برای مثال ثبت پرداخت باید در وضعیت مالی فراگیر اثر بگذارد و صدور مدرک باید با شرایط صدور تعریف‌شده مطابقت داشته باشد.

**قاعده نهم:** پیش از افزودن یک قابلیت جدید، ساختار فعلی پروژه و کدهای موجود را بررسی کن تا از تخریب قابلیت‌های پیاده‌سازی‌شده جلوگیری شود.

**قاعده دهم:** برای ساده‌ترشدن توسعه، امنیت، صحت داده‌ها یا الزامات اصلی نصب را قربانی نکن.

**قاعده یازدهم:** از ساخت امکانات غیرضروری که باعث پیچیدگی زیاد، کندی یا افزایش ریسک نگهداری می‌شوند خودداری کن.

**قاعده دوازدهم:** اگر درباره انتخاب فناوری یا جزئیات اجرا چند راهکار وجود دارد، بهترین گزینه سازگار با الزامات پروژه را انتخاب کن و دلیل فنی آن را کوتاه توضیح بده.

**قاعده سیزدهم:** اگر با محدودیت فنی واقعی روبه‌رو شدی، آن را شفاف گزارش کن و نزدیک‌ترین راهکار عملی را ارائه بده. قابلیت پیاده‌سازی‌نشده را کامل یا تست‌شده معرفی نکن.

**قاعده چهاردهم:** هر مرحله باید خروجی قابل بررسی داشته باشد؛ مانند فایل‌های واقعی، migration، تست یا مستندات.

**قاعده پانزدهم:** کد را طوری تولید کن که یک توسعه‌دهنده بتواند پس از تحویل، پروژه را بدون وابستگی به گفت‌وگوی فعلی نگهداری کند.

۳۰. ترتیب انجام کار

۲۱. داشبورد آمار را از اطلاعات واقعی پایگاه داده استخراج کند.

۲۲. کاربری فاقد مجوز نتواند با دست‌کاری URL یا درخواست API به اطلاعات خصوصی کاربران دیگر یا کلاس‌های غیرمجاز دسترسی پیدا کند.

۲۳. یک به‌روزرسانی پایگاه داده از طریق روش مستندشده انجام شود، بدون آنکه اطلاعات موجود به‌صورت ناخواسته از بین بروند.

اگر هرکدام از این سناریوها شکست خورد، علت را مشخص کن، اصلاحات لازم را انجام بده و دوباره تست کن.

اکنون پروژه را با تحلیل معماری شروع کن و بلافاصله وارد پیاده‌سازی واقعی شو. در پایان هر مرحله، فایل‌های ساخته‌شده، وضعیت تست‌ها و کارهای باقی‌مانده را گزارش کن.

هدف نهایی، تحویل یک سامانه مدیریتی واقعی، قابل نگهداری، امن، توسعه‌پذیر و قابل نصب در محیط عملیاتی است؛ نه صرفاً تولید یک نمونه نمایشی.
