# پرامپت اجرایی: پلتفرم مدیریت مؤسسه آموزشی (Node.js + cPanel بدون SSH)

> نسخه بهبودیافته. ساختار: بخش‌های ۰ تا ۹ «لایه کنترلی» (تصمیم‌ها، فازبندی، قواعد) و پیوست A «نیازمندی‌های تفصیلی» است. در تعارض، لایه کنترلی مقدم است.

---

## ۰. نقش و مأموریت

تو یک تیم مهندسی هستی: معمار نرم‌افزار، توسعه‌دهنده ارشد Node.js/TypeScript، متخصص پایگاه داده، مهندس امنیت، طراح UI/UX فارسی (RTL)، متخصص هاست cPanel و مهندس QA.

مأموریت: طراحی و پیاده‌سازی یک سامانه واقعی، امن و توسعه‌پذیر برای مدیریت مؤسسه آموزشی که **روی هاست اشتراکی cPanel و بدون SSH** نصب شود. این پروژه نمونه نمایشی نیست: هر قابلیت باید به پایگاه داده واقعی متصل باشد، کنترل دسترسی در سمت سرور اعمال شود و تست داشته باشد.

---

## ۱. اصول غیرقابل مذاکره

1. هیچ قابلیت اصلی با TODO، داده ثابت، Mock، دکمه نمایشی یا پیام «به‌زودی» جایگزین نشود.

2. هیچ عملیات حساسی فقط با کنترل فرانت‌اند محافظت نشود. هر درخواست در سمت سرور احراز هویت، مجوز و مالکیت داده را بررسی کند.

3. هیچ قابلیتی «کامل» اعلام نشود مگر تست آن واقعاً اجرا و نتیجه‌اش گزارش شده باشد. گزارش باید سه وضعیت را جدا کند: **موفق / ناموفق / اجرا‌نشده**.

4. اگر محدودیت فنی واقعی وجود دارد (هاست، API، کتابخانه)، آن را صریح بگو و نزدیک‌ترین راه‌حل عملی را بده. ادعای سازگاری غیرواقعی ممنوع است.

5. اولویت هنگام تعارض: **امنیت و صحت داده > نصب بدون SSH > کامل‌بودن قابلیت > زیبایی**.

6. هیچ رمز، کلید API یا توکنی در کد، مخزن، لاگ، پاسخ API یا فایل عمومی قرار نگیرد.

7. مسیرها و پارامترهای API پیامکی را حدس نزن؛ فقط بر اساس مستندات رسمی (بخش ۶-ف) پیاده‌سازی کن.

## ۲. تصمیم‌های فناوری (ثابت؛ تغییر فقط با دلیل فنی مکتوب)

| حوزه | انتخاب | دلیل / قید |

|---|---|---|

| هدرهای امنیتی | `helmet` | |

| Rate limit | `express-rate-limit` با ذخیره در DB (نه فقط حافظه) | Passenger ممکن است چند پروسس بسازد |

| قالب UI | SSR با Nunjucks یا EJS + htmx + Alpine.js | سبک، بدون build سنگین روی هاست |

| نمودار | Chart.js (self-host، بدون CDN) | |

| تقویم شمسی | `jalaali-js` یا معادل جاوااسکریپت خالص | |

| QR | `qrcode` (JS خالص) | |

| آپلود | `multer` + تشخیص نوع واقعی با `file-type` | |

## ۳. ریسک‌های شناخته‌شده که باید در فاز ۰ حل شوند

- **PDF فارسی:** pdfmake و pdf-lib به‌صورت پیش‌فرض اتصال حروف و RTL را درست انجام نمی‌دهند. در فاز ۰ یک spike بساز: گواهی نمونه با فونت embed شده (مثلاً وزیرمتن)، اعداد فارسی و متن مختلط. اگر خروجی صحیح نبود، به ترتیب این گزینه‌ها را بسنج: (الف) افزودن مرحله شکل‌دهی متن قبل از رندر، (ب) قالب HTML/CSS مخصوص چاپ با دکمه «چاپ / ذخیره PDF» در مرورگر. نتیجه و تصمیم را در `docs/decisions/pdf.md` سبت کن. Puppeteer/Chromium ممنوع.

- **صف پیامک:** پردازش پس‌زمینه فقط با Cron گرافیکی cPanel قابل اتکاست. دو روش پیاده‌سازی و مستند کن: (۱) فرمان cron که اسکریپت Node `dist/jobs/run.js`) را اجرا کند، (۲) فرمان cron که یک endpoint داخلی محافظت‌شده با توکن مخفی را فراخوانی کند. اگر هاست Cron نداشت، محدودیت را مستند کن و به درخواست‌های تصادفی وب وابسته نشو.

- **Node.js Selector:** اگر هاست اجرای Node، تعیین Application Startup File یا نصب وابستگی بدون SSH را ندارد، نصب بدون SSH قابل تضمین نیست؛ این را در گزارش سازگاری و راهنما صریح بنویس.

- **محدودیت منابع:** سقف RAM/پروسس هاست را در طراحی (صفحه‌بندی، پردازش مرحله‌ای، بدون بارگذاری کل داده در حافظه) لحاظ کن.

- **دسترسی اینترنت به مستندات IPPanel:** اگر محیط اجرایی تو اینترنت ندارد، فاز IPPanel را انجام نکن و به‌جای حدس‌زدن، فقط ساختار Adapter و UI را بساز، بخش‌های وابسته به API را «تأییدنشده» علامت بزن و از من مستندات بخواه.

## ۶. شاخص‌های اجرایی

### الف) نصب روی cPanel بدون SSH

- بارگذاری ZIP از File Manager و Extract.

- راه‌اندازی از Setup Node.js App: نسخه Node، Application root، Application URL، Startup File و متغیرهای محیطی.

- `node_modules` داخل ZIP یا استفاده از دکمه Run NPM Install.

- نصب‌کننده وب: بررسی سازگاری (نسخه Node، نوشتن‌پذیری مسیرها، اتصال DB، متغیرهای محیطی، اندازه آپلود) ← ساخت جداول/ایندکس‌ها/داده اولیه ← ساخت مدیر اصلی ← قفل نصب (فایل قفل خارج از مسیر عمومی + علامت در DB).

- پس از نصب، مسیر نصب‌کننده غیرفعال و قابل نصب مجدد ناخواسته نباشد.

- فایل SQL مستقل نصب/بازیابی به‌عنوان مسیر جایگزین.

- خطاهای نصب فارسی و قابل فهم، بدون افشای مسیر یا جزئیات سرور.

- صفحه سلامت (فقط مدیر): اتصال DB، نسخه Node، وضعیت migrationها، فضای دیسک، آخرین خطاهای مهم.

- اطلاعات محرمانه در متغیرهای محیطی یا مسیر خارج از وب‌روت.

### ب) داده، تاریخ و پول

- مبالغ: عدد صحیح `BIGINT`) به کوچک‌ترین واحد پول؛ هرگز `FLOAT`.

- تاریخ/زمان: ذخیره به‌صورت UTC `DATETIME`) و تاریخ تقویمی خالص `DATE`) برای جلسات؛ تبدیل شمسی فقط در لایه نمایش/ورودی، با تست سال کبیسه و مرز ماه‌ها.

- ارقام فارسی/عربی در ورودی (تلفن، مبلغ، عدد) پیش از اعتبارسنجی نرمال‌سازی شوند؛ شماره موبایل به قالب استاندارد واحد.

- حذف نرم (soft delete) برای رکوردهای مالی/آموزشی؛ حذف آبشاری ناخواسته ممنوع؛ تراکنش DB در عملیات چندمرحله‌ای.

- قیدهای یکتا و ایندکس: شماره دانشجویی، کد کلاس، کد پیگیری، کد مدرک، یک حضور برای هر (فراگیر، جلسه)، یک سبت‌نام فعال برای هر (فراگیر، کلاس)، کلید idempotency برای پرداخت و پیامک.

### پ) امنیت

- RBAC با مجوز مستقل برای هر عملیات حساس؛ نقش‌های سفارشی؛ نقش‌های سیستمی غیرقابل حذف؛ جلوگیری از ارتقای دسترسی توسط خود کاربر.

- سیاست مالکیت داده: Policy Layer مرکزی که برای هر منبع (کلاس، فراگیر، پرداخت، فایل، مدرک) «مجوز + مالکیت/عضویت» را بررسی کند؛ همه سرویس‌ها از آن استفاده کنند.

- حفاظت: CSRF، XSS (خروجی‌گذاری امن)، SQL Injection (پارامتری)، IDOR، rate limit ورود و عملیات حساس، قفل موقت پس از تلاش‌های ناموفق، هدرهای امنیتی، کوکی امن.

- فایل‌ها: تشخیص نوع واقعی، سقف اندازه، نام تصادفی، جلوگیری از Path Traversal و اجرا، ذخیره خارج از وب‌روت، دانلود فقط از مسیر کنترل‌شده با بررسی مالکیت.

- CSV: جلوگیری از Formula Injection (پیشوند‌گذاری سلول‌هایی که با `= + - @` شروع می‌شوند).

- audit log برای: ورود موفق/ناموفق، تغییر نقش/مجوز، تنظیمات امنیتی/مؤسسه/IPPanel، تأیید/رد پرداخت، اصلاح حضور و غیاب، صدور/لغو مدرک، حذف یا غیرفعال‌سازی. بدون سبت رمز/کلید در لاگ.

- MFA به‌صورت ماژول اختیاری (در صورت زمان؛ طراحی رابط آماده باشد).

### ت) کلاس‌ها، حضور و غیاب، مالی، مدارک

جزئیات در پیوست A. نکات کلیدی که باید تست شوند:

- تخصیص استاد/تغییر آن، سوابق جلسات و حضور را از بین نبرد.

- تضاد زمانی جلسات (استاد/مکان) شناسایی یا هشدار داده شود.

- رسید کارت‌به‌کارت تا تأیید کاربر مالی، پرداخت قطعی نیست؛ تأیید تکراری و سبت دوگانه ممکن نباشد.

- مدرک فقط با تحقق شرایط (حضور و وضعیت مالی طبق تنظیمات) صادر شود؛ صفحه عمومی اعتبارسنجی فقط حداقل اطلاعات را نشان دهد و لغو را منعکس کند.

### ث) داشبورد

همه شاخص‌ها و نمودارها از پرس‌وجوی واقعی DB محاسبه شوند؛ محتوا بر اساس نقش و مجوز تغییر کند؛ داده نمایشی ممنوع.

### ج) IPPanel

- مستندات مرجع: [https://ippanelcom.github.io/Edge-Document/docs/](https://ippanelcom.github.io/Edge-Document/docs/) ؛ Base URL: [https://edge.ippanel.com/v1](https://edge.ippanel.com/v1)

- پیش از پیاده‌سازی هر عملیات (احراز هویت، ارسال ساده، ارسال با پترن، وضعیت پیامک)، صفحه همان عملیات را بخوان و مسیر، بدنه، هدر و قالب پاسخ را از آن بگیر.

- Adapter مستقل پشت یک رابط `SmsProvider` (قابلیت افزودن ارائه‌دهنده دیگر).

- API Key فقط سمت سرور، رمزنگاری‌شده در ذخیره‌سازی (کلید از env)، ماسک در UI، هرگز در لاگ.

- رویدادها قابل تعریف: هر رویداد ← فعال/غیرفعال، کد پترن، متغیرهای موردنیاز، **نگاشت** نام متغیر داخلی به نام متغیر پترن، منبع استخراج هر متغیر، مقدار پیش‌فرض، شرط اجرا، مخاطب، تأخیر، سیاست تلاش مجدد.

- پیش از ارسال: بررسی وجود و اعتبار متغیرهای ضروری؛ در نبود، ارسال نشود و خطای قابل فهم سبت شود.

- جلوگیری از ارسال تکراری (کلید یکتا برای هر رویداد+موجودیت+مخاطب)، محدودیت نرخ، تلاش مجدد کنترل‌شده با backoff، صف DB، ارسال آزمایشی برای مدیر مجاز.

- تست‌ها هرگز پیامک واقعی نفرستند مگر با پیکربندی صریح `SMS_LIVE_TESTS=1`)؛ در حالت عادی از Fake Provider استفاده شود.

## ۸. معیار پذیرش نهایی (سناریوی end-to-end)

پروژه فقط وقتی تحویل‌شدنی است که این سناریو (ترجیحاً به‌صورت تست خودکار + چک‌لیست دستی نصب) اجرا و گزارش شود:

1. نصب با راهنما از طریق رابط گرافیکی cPanel بدون SSH.

2. سبت اطلاعات مؤسسه.

3. ساخت نقش جدید و تخصیص مجوز.

4. سبت یک استاد و چند فراگیر.

5. ساخت کلاس با زمان، جلسات و شهریه.

6. تخصیص استاد به کلاس.

7. فعال‌سازی فرم پیش‌سبت‌نام.

8. تبدیل درخواست متقاضی به سبت‌نام قطعی (بدون کاربر/سبت‌نام تکراری).

9. ورود فراگیر و مشاهده فقط اطلاعات خودش.

10. ورود استاد و مشاهده فقط کلاس‌های خودش.

11. سبت حضور و غیاب یک جلسه.

12. انعکاس آن در گزارش‌های مجاز.

13. تعریف شهریه و اقساط برای فراگیر.

14. سبت رسید کارت‌به‌کارت و بررسی توسط کاربر مالی.

15. به‌روزرسانی وضعیت مالی و مانده طبق پرداخت تأییدشده.

16. صدور مدرک پس از تحقق شرایط و نمایش در حساب فراگیر.

17. اعتبارسنجی مدرک با کد/QR در صفحه عمومی.

18. سبت اتصال IPPanel و یک پترن.

19. استخراج و نگاشت متغیرها از داده واقعی.

20. ارسال واقعی پیامک (در صورت وجود دسترسی API) و پیگیری نتیجه.

21. داشبورد از داده واقعی.

22. ناکامی دسترسی غیرمجاز با دست‌کاری URL/API (IDOR).

23. اجرای migration نسخه جدید بدون از دست رفتن داده.

سناریوی ناموفق: علت را مشخص کن، رفع کن، دوباره تست کن؛ و در گزارش بنویس. سناریوی اجرا‌نشده (مثلاً ۲۰ بدون API Key) را «اجرا‌نشده + دلیل» سبت کن، نه «موفق».

- گزارش واقعی تست‌ها

# پیوست A: نیازمندی‌های تفصیلی (فشرده)

## A1. تنظیمات مؤسسه و هویت بصری

نام رسمی و تجاری، لوگو، شعار، توضیحات، تلفن/موبایل/ایمیل/نشانی/وب‌سایت/شبکه‌های اجتماعی، شناسه‌های سبتی، اطلاعات مدیر، امضای مسئول صدور، مهر، رنگ‌های اصلی، سربرگ، اطلاعات پیش‌فرض مدارک و رسیدها. استفاده در داشبورد، پنل‌ها، پیامک، گواهی، رسید و گزارش؛ تغییر بدون ویرایش کد.

## A2. کاربران، نقش‌ها، RBAC

- نقش‌های پیش‌فرض: مدیر سامانه، مدیر اجرایی، مدیر آموزش، کارمند سبت‌نام، کارمند مالی، مسئول حضور و غیاب، استاد، فراگیر؛ + نقش‌های سفارشی.

- مجوز = ماژول + منبع + عملیات (مشاهده، ایجاد، ویرایش، حذف، تأیید/رد، سبت/تایید پرداخت، صدور/لغو مدرک، مشاهده گزارش، خروجی، مدیریت تنظیمات).

- ایجاد/ویرایش/غیرفعال‌سازی نقش، مشاهده کاربران هر نقش، حداقل دسترسی، اثر فوری تغییر نقش.

- فعال/غیرفعال‌کردن حساب، تغییر و بازنشانی امن رمز، خروج از نشست‌ها، مشاهده سوابق امنیتی.

## A3. کنترل دسترسی سطح داده

استاد فقط کلاس‌های تخصیصی؛ فراگیر فقط داده خود (پروفایل، سبت‌نام، برنامه، حضور، مالی، مدارک)؛ بدون دسترسی با تغییر ID؛ کارمند سبت‌نام/مالی بدون ارتقای مجوز؛ APIهای خروجی و Export هم تابع همین قواعد. تست‌های اختصاصی منفی (negative authorization tests) برای همه منابع.

## A4. اساتید

مشخصات، تماس، تصویر، کد داخلی، تخصص‌ها، سوابق، وضعیت و تاریخ شروع همکاری، یادداشت مدیریتی محدود، کلاس‌ها، تعداد فراگیران، برنامه تدریس، جلسات برگزارشده، حضور و غیاب کلاس‌های خود. چند استاد برای هر کلاس؛ چند کلاس برای هر استاد؛ تغییر تخصیص بدون از بین‌رفتن تاریخچه.

## A5. دوره‌ها، کلاس‌ها، جلسات

- کلاس: عنوان، کد یکتا، توضیحات، نوع، دسته، سطح، استاد(ها)، ظرفیت، شهریه، تاریخ و ساعت شروع/پایان، روزها، محل، وضعیت (پیش‌نویس، در حال سبت‌نام، تکمیل ظرفیت، در حال برگزاری، پایان‌یافته، لغوشده)، پوستر، شرایط و پیش‌نیاز سبت‌نام، وضعیت انتشار پیش‌سبت‌نام، مهلت سبت‌نام، شرایط انصراف، پیوست‌ها.

- جلسه: تاریخ، ساعت، مدت، موضوع، استاد مسئول، وضعیت (برگزار/لغو/جابه‌جا) با سابقه؛ تضاد زمانی؛ حفظ سبت‌نام‌ها هنگام تغییر برنامه.

## A6. پیش‌سبت‌نام و سبت‌نام

فرم قابل پیکربندی برای هر کلاس (فیلدها، اجباری‌ها، نوع، اعتبارسنجی، آپلود با کنترل نوع/اندازه)، کد پیگیری، جلوگیری از تکرار، فهرست/جست‌وجو/فیلتر، تأیید/رد/درخواست اصلاح با علت، اعلان/پیامک وضعیت، تبدیل کنترل‌شده به سبت‌نام قطعی بدون تکرار کاربر یا سبت‌نام؛ کمترین اطلاعات ممکن در فرم عمومی؛ فرم عمومی با CAPTCHA/rate limit.

## A7. فراگیران

پرونده آموزشی، مشخصات، موبایل، تماس ضروری، سرپرست (برای دانش‌آموز)، شناسه یکتا، کد فراگیر، تاریخ عضویت، وضعیت، سبت‌نام‌ها و تاریخچه، پرداخت و اقساط، حضور، مدارک، پیوست‌ها، یادداشت محدود، تاریخچه تغییرات، جست‌وجو/فیلتر، ورود گروهی CSV (اعتبارسنجی + گزارش خطای هر سطر + پیش‌نمایش)، خروجی مجاز، انتقال به کلاس جدید با حفظ تاریخچه.

## A8. حضور و غیاب

جلسه‌محور؛ وضعیت‌ها: حاضر، غایب، تأخیر، غیبت موجه، سبت‌نشده؛ سبت سریع کل کلاس؛ توضیح غیبت؛ سبت زمان و کاربر؛ اصلاح با سابقه (audit)؛ یکتایی (فراگیر، جلسه)؛ گزارش جلسه/کلاس/فراگیر؛ درصد حضور؛ حد مجاز غیبت و هشدار؛ فیلترها؛ خروجی PDF/CSV با کنترل دسترسی.

## A9. مالی

- روش‌ها: نقدی، یکجا، اقساطی، کارت‌به‌کارت، سبت دستی؛ قابل پیکربندی؛ آماده اتصال درگاه آینده (رابط `PaymentGateway`).

- اقساط: تعداد، مبلغ، سررسید، پرداخت جزئی/کامل، مانده، معوق، توضیح، تاریخ، کاربر سبت‌کننده، تاریخچه، بدهی کل/معوق، هشدار و یادآوری پیامکی.

- کارت‌به‌کارت: آپلود رسید توسط فراگیر، وضعیت «در انتظار بررسی»، تأیید/رد با علت/درخواست رسید مجدد، سابقه بررسی، جلوگیری از تأیید/سبت دوگانه و دست‌کاری مبلغ.

- هر تراکنش: شناسه یکتا + تاریخچه تغییر (دفتر کل append-only)؛ اصلاح با تراکنش معکوس، نه ویرایش مبلغ.

- اسناد: رسید پرداخت، گزارش بدهکاران، درآمد، اقساط، مالی کلاس‌ها. دسترسی مالی جدا از آموزشی.

## A10. مدارک

قالب‌ها (بارگذاری/طراحی)، لوگو، نام فراگیر، دوره، تاریخ‌ها، شماره/کد یکتا، مسئول، امضا/مهر، متن و ظاهر قابل تنظیم، PDF چاپی با فونت فارسی صحیح، شرایط صدور (حضور/مالی)، صدور گروهی (پردازش مرحله‌ای)، سبت سوابق، لغو با دلیل، بازتولید فایل بدون تغییر کد، QR به صفحه اعتبارسنجی عمومی با حداقل اطلاعات و نمایش وضعیت لغو.

## A11. تنظیمات

دسته‌ها: عمومی، ظاهر، تاریخ/زمان، سبت‌نام، کلاس‌ها، حضور و غیاب، مالی، مدارک، پیامک، امنیت، کاربران، اعلان‌ها، فایل‌ها، پشتیبان‌گیری، سامانه. هر تنظیم: نوع، اعتبارسنجی (Zod)، پیش‌فرض، سطح دسترسی؛ مقادیر حساس ماسک؛ تغییر حساس در audit؛ جدول تنظیمات بدون‌ساختار و نامحدود ممنوع.

## A12. داشبورد و گزارش

شاخص‌ها: فراگیران (کل/فعال)، اساتید فعال، کلاس‌ها به تفکیک وضعیت، پیش‌سبت‌نام‌ها (کل/در انتظار)، جلسات امروز، حضور و غیاب، شهریه سبت‌شده، دریافتی، مانده مطالبات، اقساط سررسیدشده، پرداخت‌های منتظر تأیید، مدارک صادرشده، وضعیت پیامک، خطاهای مهم (مدیران).

نمودارها (هرکدام با هدف مشخص): روند سبت‌نام، مقایسه کلاس‌ها، روند درآمد، توزیع وضعیت پرداخت، حضور و غیاب، ظرفیت در برابر سبت‌نام، آمار پیامک. فیلتر زمانی/کلاس، جزئیات، خروجی.

## A13. رابط کاربری

فارسی، RTL واقعی، واکنش‌گرا (موبایل/تبلت/دسکتاپ)، منوی جمع‌شونده، جدول با فیلتر/مرتب‌سازی/صفحه‌بندی سمت سرور، فرم‌های گروه‌بندی‌شده با خطای کنار فیلد، حالت خالی با راهنما، تأیید عملیات حساس، چاپ مناسب، دسترس‌پذیری و کنتراست، تقویم شمسی. Design System و کامپوننت‌های مشترک؛ بدون رنگ‌ها و تراکم نامرتبط. فونت و دارایی‌ها self-host.

## A14. پنل استاد

کلاس‌ها، برنامه، فهرست فراگیران کلاس‌های خود (فقط فیلدهای مجاز)، سبت حضور و غیاب، سوابق جلسات، توضیح جلسه، گزارش کلاس‌های خود، اعلان‌ها، ویرایش اطلاعات شخصی مجاز. بدون دسترسی پیش‌فرض به مالی، تنظیمات و کلاس‌های دیگر.

## A15. پنل فراگیر

پروفایل، کلاس‌ها، برنامه و جلسات، حضور و غیاب خود، شهریه/اقساط/پرداخت‌ها، آپلود رسید و نتیجه بررسی، مدارک و دانلود، اعلان‌ها، وضعیت سبت‌نام، تغییر رمز. موبایل‌محور؛ فقط داده خود یا اطلاعات عمومی کلاس.

## A16. فایل‌ها و پشتیبان‌گیری

- فایل‌ها: مسیر قابل پیکربندی خارج از وب‌روت، سبت مالکیت و ارتباط با موجودیت، جایگزینی/حذف کنترل‌شده، دانلود با بررسی مجوز.

- پشتیبان: دامپ DB با کد Node (بدون `mysqldump` در صورت نبود)، پشتیبان فایل‌های ضروری (در صورت محدودیت فشرده‌سازی/زمان، پردازش مرحله‌ای و مستندسازی محدودیت)، سبت تاریخ/وضعیت، فهرست نسخه‌ها، دسترسی محدود، کنترل سازگاری پیش از بازیابی، هشدار واضح، فقط مجوز ویژه، audit.
